# Flow Workbench — development log

This document records how the tool was built and, in particular, where each part of the source code came from. It exists so that anyone auditing the tool, citing it, or relicensing it can see exactly what is original work, what follows a published specification, and what was used only for testing.

---

## 1. Provenance summary

**All source code in `flow_workbench.html` was written from scratch for this project.**

No code was copied, transpiled, decompiled or machine-translated from CytoExploreR, flowCore, flowWorkspace, openCyto, flowGate, FlowJo, FCSExpress, FlowIO, FlowKit, FlowCal, or any other cytometry package. No R code was ported to JavaScript. CytoExploreR was the model for *what the tool should do* — its workflow, its tab structure and its vocabulary — and not a source of code.

The application bundles **no third-party JavaScript libraries**. There is no jQuery, React, D3, Plotly, or charting library. Everything uses built-in browser APIs: Canvas 2D, `DataView`/`TypedArray`, `CompressionStream`, and the File System Access API where present. This is why the tool is a single file with no build dependencies and no network access.

What *is* derived from outside sources, and how:

| Component | Derived from | Nature of the derivation |
|---|---|---|
| FCS file reader | FCS 2.0 / 3.0 / 3.1 published standards | Implemented from the specification documents |
| Logicle transform | Parks, Roederer & Moore (2006); Moore & Parks (2012) | Implemented from the published equations |
| Compensation convention | flowCore documentation | Convention only (`raw %*% solve(S)`), no code |
| Spillover from controls | Standard community practice | Median-positive minus median-negative method |
| Robust CV | Standard flow cytometry convention | (84.13th − 15.87th percentile) / 2 / median |
| Test FCS files | `whitews/FlowIO` repository | Read-only validation inputs, **not redistributed** |
| Validation oracle | `flowio` Python package (BSD-3) | Used in the build container only, **not bundled** |
| Demo dataset | None — synthetic | Generated by a seeded PRNG written for this project |

## 2. Algorithm provenance in detail

### FCS parsing (`core.js`)

Written against the published FCS standards:

- Dean, P.N. et al. (1990) *Data file standard for flow cytometry.* Cytometry 11:323–332. (FCS 2.0)
- Seamer, L.C. et al. (1997) *Proposed new data file standard for flow cytometry, version FCS 3.0.* Cytometry 28:118–122.
- Spidlen, J. et al. (2010) *Data file standard for flow cytometry, version FCS 3.1.* Cytometry A 77:97–100.

Implemented from those documents: the HEADER offset block, the delimited TEXT segment with doubled-delimiter escaping, `$DATATYPE` I/F/D, `$BYTEORD` endianness, `$PnB` bit widths with `$PnR` range masking, and `$PnE` log amplification converted to linear on read.

Two robustness behaviours were added after observing real files during testing, and are not in the standard:

- When HEADER and TEXT disagree on the data segment offsets, whichever pair matches `$TOT × row size` is used. Two files in the FlowIO test set have this discrepancy.
- When `$TOT` exceeds what the data segment can hold, the event count is recomputed from the segment size. This is what allowed the multi-dataset `coulter.lmd` file to be read at all.

### Logicle transform (`core.js`)

Implemented from the published equations in:

- Parks, D.R., Roederer, M. & Moore, W.A. (2006) *A new "Logicle" display method avoids deceptive effects of logarithmic scaling for low signals and compensated data.* Cytometry A 69:541–551.
- Moore, W.A. & Parks, D.R. (2012) *Update for the logicle data scale including operational code implementations.* Cytometry A 81:273–277.

The biexponential form `S(y) = a·e^(by) − c·e^(−dy) + f` is evaluated directly. Two implementation choices are mine rather than the paper's:

- The parameter `d` is solved by **200-step bisection** on the constraint equation, rather than by the Taylor-series root-finding used in the reference C++ implementation. Bisection is slower but trivially correct and has no convergence edge cases.
- The **inverse** is built as a 16,384-point lookup table over the scale interval [−0.4, 1.4] with binary search and linear interpolation between points, rather than Newton iteration per value. This makes transforming millions of events fast enough for interactive redraws.

Automatic width estimation uses `W = (M − log10(T/|r|)) / 2` where `r` is the fifth percentile of negative events — the heuristic described in the 2006 paper. Round-trip accuracy was measured at a maximum relative error of 1.5 × 10⁻⁷.

### Compensation (`core.js`)

The spillover matrix is inverted by Gauss-Jordan elimination with partial pivoting, written directly. Compensated values are computed as `raw %*% solve(S)`, which is the convention documented for flowCore and used by the FCS `$SPILLOVER` keyword; adopting a documented convention is not code derivation. A singular matrix raises an error rather than producing silent nonsense.

Spillover estimation from single-stain controls uses the standard approach: take events between the 95th and 99.8th percentile of the primary detector as the positive population, subtract the negative median (from the unstained control if supplied, otherwise from the dim half of the same control), and divide each secondary detector's signal by the primary's. This method is community standard practice rather than any one package's code.

### Other original components

- **Density rendering** — counts events into a bin grid, colours by `log1p(count)` normalised to the maximum, and draws the result as a nearest-neighbour-scaled `ImageData`. The six-stop colour ramp (`#1F3BB3 → #14A6C8 → #3DB54A → #F1D30F → #F08A0C → #D7261E`) was chosen by hand for this project; it is not viridis, jet, or any ported colormap.
- **Gate geometry** — ray-casting point-in-polygon, with rectangles, ellipses and quadrants reduced to polygon or comparison tests. Gates are stored in **raw data units**, so changing a transform moves the gate with the data rather than stranding it on screen.
- **Histogram smoothing** — 220 bins convolved with a fixed 5-point kernel `[0.06, 0.24, 0.40, 0.24, 0.06]`.
- **FCS writer** — minimal FCS 3.1 float32 writer, used for exporting gated populations.
- **SVG recorder** (`svgctx.js`) — a class implementing the subset of the Canvas 2D API that the plotting code uses (`beginPath`, `arc`, `fillText`, `clip`, `drawImage`, transform stack, and so on) and emitting SVG elements instead of pixels. This is what lets a single drawing routine produce both the screen view and a vector figure. Written from the Canvas 2D and SVG 1.1 specifications.
- **Demo dataset** — fully synthetic. A seeded mulberry32-style PRNG with a Box-Muller normal generator produces log-normal fluorescence populations, which are then multiplied by a known spillover matrix to create realistic uncompensated data. No real donor or patient data is included anywhere in the file. Because the true spillover matrix is known by construction, it doubles as a correctness test for the compensation solver.

### Notable problems and how they were resolved

**Data offset discrepancies.** Two test files disagree between HEADER and TEXT about where the data segment starts or ends. Resolution: prefer whichever offset pair is consistent with `$TOT × row size`.

**Logicle axes started at zero.** The default range began at the scale zero point, clipping the negative events that logicle exists to display. Resolution: derive the lower bound from the 0.05th percentile of the data.

**The save dialog that never opens.** `showSaveFilePicker` exists in some contexts where it cannot actually display a dialog; it rejects immediately with `AbortError` — indistinguishable from a user cancelling. Resolution: time the rejection. Under 250 ms means no human saw a dialog, so fall back to a download; over 250 ms is treated as a genuine cancellation.

**Projects lost file metadata.** The first version re-encoded each sample as float32 on save. Resolution: keep the original bytes.

Two design notes worth recording. Because a sample can be in two groups that gate it differently, **a population is the pair (group, gate)** rather than a gate alone, and the active group resolves the ambiguity everywhere it matters. Overrides are stored separately from gates rather than as modified copies, so renaming or reshaping a group's gate does not strand the per-sample adjustments hanging off it, and removing a sample from a group discards only that sample's overrides for that group's gates.

## 4. Testing

**Reference comparison.** The parser was checked against `flowio` (Python, BSD-3-Clause) on nine FCS files spanning FCS 2.0/3.0/3.1, integer/float data types, both byte orders, variable bit widths, log-amplified channels, offset discrepancies and a multi-dataset LMD file. First event, last event and per-channel means were compared. Float files matched exactly; the largest disagreement anywhere was 3 × 10⁻⁸ relative, from float32 rounding. Log-amplified integer channels differ by design, since the tool converts `$PnE` channels to linear scale on read.

**Compensation.** Recovered spillover coefficients from synthetic single-stain controls agreed with the known ground-truth matrix to within 0.0005 in absolute spillover fraction, both with and without an unstained control.

**Logicle.** Forward-then-inverse round trip across −5,000 to 262,144 gave a maximum relative error of 1.5 × 10⁻⁷.

**End-to-end.** Playwright scripts drive the real UI: drawing polygon, rectangle, interval and quadrant gates by simulated mouse input; switching tabs; computing compensation from controls; exporting CSV, FCS, PNG and SVG; saving and reopening projects. Exported SVG was rendered back in a browser and compared with the canvas output. Population counts after a project round trip were identical to the originals.

**Test data.** FCS files came from the `whitews/FlowIO` repository's `data/fcs_files` directory. They were used **only as read-only inputs inside the build container**. No test file is included in or redistributed with the application.

## 5. Source layout

The distributed `flow_workbench.html` is assembled by `build.py`, which inlines five source files into a single HTML shell. There is no minifier, bundler or transpiler; the shipped code is the source code, readable in any text editor or via View Source.

```
shell.html    415 lines   markup and CSS
core.js       496 lines   FCS I/O, transforms, compensation, gates, statistics  (DOM-free)
ui.js         955 lines   rendering, interaction, sidebar, four original tabs
svgctx.js      79 lines   Canvas-2D-compatible SVG recorder
project.js    140 lines   .fwproj save/open, dirty tracking, File menu
export.js     290 lines   figure layouts, preview, PNG/SVG/PDF output
groups.js     188 lines   group model, membership, per-sample gate overrides
free.js       277 lines   free-form canvas: item model, editing, annotations
build.py                  inlines the above into flow_workbench.html
```

Everything runs client-side. The application makes no network requests of any kind.

## 6. Licensing notes

Because no third-party code is bundled, the application carries no inherited license obligations. The FCS standards are published specifications, and implementing a specification does not create a derivative work of any implementation of it. The logicle papers describe an algorithm; the equations were implemented independently rather than by copying the authors' reference code, which carries its own license terms.

If you intend to redistribute this tool, two points are worth noting. First, `flowio` and the FlowIO test files were used during development but are absent from the distributed file; they impose no obligation on it. Second, if you later choose to vendor the authors' reference logicle implementation in place of the version here, its license would then apply — that substitution has not been made.

CytoExploreR itself is GPL-3 licensed. Nothing in this tool derives from it, so that license does not reach this code. If you publish work using this tool alongside CytoExploreR, cite CytoExploreR for anything actually produced with it.

## 7. Known limitations

- This is an independent implementation, not a validated equivalent of CytoExploreR or FlowJo. Cross-check key numbers before publishing.
- No dimensionality reduction (tSNE, UMAP), no automated gating (openCyto), no FlowJo workspace import.
- All files in one session must share channel names.
- Compensation from controls assumes one dominant fluorochrome per control file.
- Very large files are bounded by browser memory, since all events are held as `Float32Array` columns.
